## Security Report Backend Data Integration Requirement

Currently, the security report generation module for the Web Security Penetration Testing Platform relies on static data and mock objects. This approach is acceptable for demonstration and UI validation purposes; however, it is not suitable for generating real security reports for actual penetration testing projects.

For production-level security reports, the system must retrieve real vulnerability data stored in the database for each registered project. All reported vulnerabilities are stored separately in the database, and each vulnerability record contains the related project identifier to determine which project the vulnerability belongs to.

The security report generation process should only include verified vulnerabilities. In other words, the report must include only vulnerability records where the `state` field value is equal to `Verify`. Any vulnerability that has not been verified should not be included in the final security assessment report.

In the current backend architecture, a dedicated vulnerability model has already been implemented for managing discovered security issues. This model is defined in the following file:

```
vulnerability.model.ts
```

This model is responsible for storing and managing all discovered vulnerabilities during security testing activities.

The security report module should retrieve project vulnerabilities using the following criteria:

1. The vulnerability record must belong to the target project.
2. The vulnerability project identifier must match the requested project ID.
3. The vulnerability status must be:

```
state = Verify
```

Only vulnerabilities satisfying these conditions should be included in the final Web Security Penetration Testing Report.

## Project Reference Field Compatibility

In the previous version of the system (approximately two years ago), the vulnerability model used a field named `project` to store the reference ID of the related project.

In the current version of the system, a new field named `projectId` has been introduced to improve naming consistency and database structure clarity. However, the previous `project` field has intentionally been kept in the model to maintain backward compatibility with the legacy system.

The current model contains both fields:

```typescript
projectId: { 
    type: Schema.Types.ObjectId, 
    ref: "Project" 
},

project: { 
    type: Schema.Types.ObjectId, 
    ref: "Project" 
}
```

The backend implementation should consider both fields during the migration period to ensure compatibility with existing vulnerability records.

The recommended approach is:

- Use `projectId` as the primary reference field for all new vulnerability records.
- Continue supporting `project` for legacy vulnerability data.
- When generating security reports, the query logic should handle both fields to ensure that all valid vulnerabilities belonging to a project are retrieved correctly.

## Required Backend Implementation

The backend team should analyze and implement the required APIs for the security reporting module with the following objectives:

- Replace all static and mock vulnerability data with real database queries.
- Retrieve vulnerabilities dynamically based on project ID.
- Filter vulnerabilities based on verification status.
- Integrate the vulnerability model with the security report generation workflow.
- Ensure backward compatibility with existing vulnerability records.
- Implement proper validation and authorization mechanisms.
- Provide scalable and maintainable APIs for generating accurate security assessment reports.

The final goal is to transform the current prototype-based reporting system into a fully database-driven security reporting platform capable of generating real penetration testing reports based on verified vulnerabilities stored in the system.
