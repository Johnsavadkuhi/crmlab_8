# گزارش بررسی امنیت، پایداری و پرفورمنس

تاریخ: ۲۰۲۶-۰۹-۱۹

## نتیجه و دامنه بررسی

ساختار کل مخزن با راهنمای `AGENTS.md` و نمایه پروژه مرور شد. بررسی دقیق روی احراز هویت، نقش‌ها و مجوزها، آپلود و دانلود، نشست‌ها، اعلان‌ها و Socket.IO، تنظیمات استقرار، مسیرهای اصلی فرانت‌اند و وابستگی‌ها متمرکز بود. تست‌های موجود حوزه‌های پروژه، تخصیص، دارایی، داشبورد، استانداردها، آسیب‌پذیری، 4L و سازگاری دیتابیس قدیمی نیز اجرا شدند.

اصلاحات در کد محلی انجام شده‌اند. دیتابیس واقعی، فایل‌های کاربران و سرویس production تغییر داده نشده‌اند. نتیجه این بررسی تضمین نبودن تمام باگ‌های احتمالی یا جایگزین تست نفوذ و آزمون کامل محیط واقعی نیست.

نتیجه نهایی اعتبارسنجی:

| بررسی | نتیجه |
| --- | --- |
| تست‌های بک‌اند | ۱۹۲ تست موفق، صفر شکست |
| تست‌های فرانت‌اند | ۴۲ تست موفق، صفر شکست |
| `npm run typecheck` | موفق؛ ۱۲ خطای اولیه فرانت‌اند رفع شد |
| `npm run lint` | موفق، بدون خطا و هشدار |
| `npm run build` | ساخت بک‌اند و فرانت‌اند موفق |
| بررسی وابستگی‌ها | پس از به‌روزرسانی: صفر مورد شناخته‌شده در خروجی npm audit |
| نمایه پروژه | بازتولید کامل و بررسی سازگاری |

## اصلاحات امنیتی

### ثبت‌نام و مدیریت کاربران

- **ساخت ادمین بدون احراز هویت:** مسیر `POST /api/auth/register-admin` قبلاً عمومی بود. اکنون نیازمند نشست معتبر و نقش ادمین است. راه‌اندازی اولین ادمین از طریق seed کنترل‌شده باقی مانده است.
- **انتخاب نقش در ثبت‌نام عمومی:** ورودی `roles` از قرارداد عمومی حذف شد و سرویس ثبت‌نام نیز مستقل از اعتبارسنجی HTTP نقش پیش‌فرض قبلی، یعنی `pentester`، را اعمال می‌کند. کاربر نمی‌تواند با ارسال مستقیم JSON ادمین شود.
- **ورودی آزاد ساخت کاربر:** مسیر مدیریت کاربران اکنون schema مشخص دارد. فیلدهای داخلی مانند `_id`، `sessionVersion`، `projectIds` و پرچم‌های قدیمی نقش از ورودی حذف می‌شوند و نقش‌های غیرمعتبر رد می‌شوند. حذف فیلد permissions از درخواست با ارسال صریح آرایه خالی یکسان تلقی نمی‌شود.
- **حساب غیرفعال قدیمی:** هر دو وضعیت `isActive === false` و `status === "Inactive"` در بررسی نشست کنترل می‌شوند؛ نبودن فیلد جدید `isActive` در رکورد فعال قدیمی باعث رد اشتباه کاربر نمی‌شود.
- **حدس رمز:** روی تلاش‌های ناموفق ورود و ثبت‌نام محدودیت مستقل اضافه شد. سقف عمومی API نیز حفظ شده است.
- **رمز ثابت seed:** رمز ثابت داخل کد حذف شد. متغیر `SEED_ADMIN_PASSWORD` با حداقل ۱۲ کاراکتر لازم است. اجرای مجدد seed دیگر حساب موجود را ناخواسته بازنویسی نمی‌کند. تغییر صریح رمز حساب موجود با `SEED_ADMIN_RESET_PASSWORD=true` انجام می‌شود و نسخه نشست را افزایش می‌دهد.

فایل‌های اصلی: `apps/api/src/modules/auth/`، `apps/api/src/modules/users/`، `apps/api/src/db/seed.ts`.

### نشست و CSRF

- مصرف refresh token با شرط فعال‌بودن و انقضا، در یک عملیات اتمیک دیتابیس انجام می‌شود. دو درخواست هم‌زمان نمی‌توانند از یک token دو نشست جدید بسازند.
- پاسخ ۴۰۱ معمولی یا پاسخ ناموفق قدیمیِ refresh، کوکی تازه‌شده توسط درخواست یا تب دیگر را پاک نمی‌کند.
- درخواست‌های هم‌زمان فرانت‌اند یک عملیات refresh و یک دریافت CSRF مشترک دارند. برای تب‌های مختلف، در مرورگرهای پشتیبان از Web Locks استفاده می‌شود.
- token جدید CSRF از پاسخ احراز هویت ذخیره می‌شود. پاسخ ۴۰۳ مربوط به مجوز دیگر باعث اجرای دوباره عملیات نمی‌شود؛ retry تنها برای خطای مشخص CSRF انجام می‌شود.
- درخواست‌های امن GET/HEAD/OPTIONS برای دریافت CSRF درخواست اضافی نمی‌فرستند.
- درخواست مستقیم تصویر، ویدئو و دانلود POC جداگانه پوشش داده شده است: در صورت انقضای access token، نشست refresh معتبر می‌تواند access cookie را بدون چرخاندن refresh token تمدید کند. این مسیر برای حفظ پیش‌نمایش و دانلود بومی مرورگر لازم است و کنترل دسترسی پروژه همچنان اجرا می‌شود.

فایل‌های اصلی: `middlewares/auth.middleware.ts`، `modules/auth/services/session.service.ts`، `apps/web-fsa/src/shared/api/baseApi.ts`.

### فایل‌ها و لینک‌های فرانت‌اند

- آپلود آواتار دیگر پسوند فایل ارسالی کاربر را مبنای ذخیره قرار نمی‌دهد. پسوند از نوع تصویر مجاز انتخاب می‌شود و امضای ابتدای فایل بررسی می‌شود. HTML با MIME جعلی و SVG اجرایی پذیرفته نمی‌شوند؛ JPEG، PNG، WebP و GIF حفظ شده‌اند.
- اندازه، تعداد فایل و بخش‌های multipart محدود شده‌اند. فایل با محتوای نامعتبر از دیسک حذف می‌شود. آپلود پیش از ثبت‌نام، که رابط فعلی به آن نیاز دارد، حفظ شده است.
- پاسخ فایل‌های عمومی دارای CSP محدود و `sandbox` است تا فایل‌های قدیمی در صورت بازشدن مستقل به سند فعال هم‌مبدأ تبدیل نشوند.
- شواهد POC قدیمی که در پوشه عمومی uploads قرار دارند از مسیر عمومی مسدود می‌شوند و از مسیر دارای احراز هویت POC قابل دریافت‌اند. برای شناسایی سریع شناسه‌های قدیمی و جدید شواهد، ایندکس‌های افزایشی sparse و غیر unique هنگام راه‌اندازی ایجاد می‌شوند؛ هیچ سند یا ایندکس موجود حذف نمی‌شود.
- حذف فایل به مالک آواتار یا ادمین محدود شده است. کاربر عادی نمی‌تواند آواتار مشترک با کاربر دیگر را حذف کند. فایل شواهد نیز از مسیر عمومی حذف آپلود پاک نمی‌شود.
- لینک اعلان فقط می‌تواند مسیر داخلی برنامه باشد. لینک‌های `javascript:`، `data:`، آدرس خارجی، مسیر `//host` و مسیرهای دارای backslash یا کاراکتر کنترلی رد می‌شوند. رویداد کلیک اعلان سیستم‌عامل نیز این کنترل را مستقل اجرا می‌کند.

فایل‌های اصلی: `modules/uploads/`، `app/app.ts`، `entities/notification/model/notification.ts` و `features/notifications/browser/browserNotification.ts`.

### ارتباط زنده و استقرار

- ورودی خالی یا نامعتبر رویداد `notification:mark_read` دیگر پیش از بلوک مدیریت خطا destructure نمی‌شود. خطای راه‌اندازی اتصال نیز مدیریت می‌شود.
- پس از غیرفعال‌سازی کاربر یا تغییر دسترسی او، اتصال‌های زنده قبلی قطع می‌شوند. اعضایی که از پروژه کاملاً حذف شده‌اند از room همان پروژه خارج می‌شوند.
- در هر دو تنظیم Nginx، مسیر `/api/` بر الگوی فایل‌های استاتیک اولویت دارد. دانلود POC با پسوند تصویر دیگر نباید اشتباهاً در فایل‌های فرانت‌اند جست‌وجو شود.
- سقف بدنه Nginx به ۲۶۰ مگابایت رسید تا با سقف ۲۵۰ مگابایتی مجموع POC و سربار multipart سازگار باشد. محدودیت‌های دقیق‌تر خود برنامه باقی مانده‌اند.

## وابستگی‌ها

گزارش اولیه npm audit شامل ۱۵ مورد وابستگی آسیب‌پذیر بود: ۱۲ high و ۳ moderate. به‌روزرسانی‌ها ابتدا با dry-run بررسی و سپس بدون `--force` و با `--ignore-scripts` اعمال شدند. نسخه major هیچ‌یک از بسته‌های تغییرکرده عوض نشد.

نمونه به‌روزرسانی‌ها:

| بسته | قبل | بعد |
| --- | --- | --- |
| multer | 2.2.0 | 2.4.0 |
| morgan | 1.11.0 | 1.12.1 |
| socket.io-parser | 4.2.6 | 4.2.7 |
| react-router / react-router-dom | 7.18.0 | 7.18.4 |
| postcss | 8.5.15 | 8.5.28 |
| qs | 6.15.3 | 6.16.0 |

اصلاحات در `package-lock.json` ثبت شده‌اند. نتیجه صفر npm audit فقط ناظر به advisoryهای شناخته‌شده آن زمان است؛ امنیت منطق برنامه را به‌تنهایی اثبات نمی‌کند.

## بهبودهای پرفورمنس

| بخش | قبل | بعد و هزینه جانبی |
| --- | --- | --- |
| گروه‌بندی اعلان برای یک کاربر | کپی آرایه در هر تکرار؛ زمان و مجموع تخصیص‌های موقت O(n²) | افزودن به آرایه همان گروه؛ زمان O(n)، خروجی O(n) |
| یافتن کاربر در تب‌های تخصیص | برای هر شناسه یک `find`؛ O(m×n) | Map با ساخت O(n) و lookupهای O(m)؛ حافظه اضافه O(n) |
| تطبیق scope | `includes` داخل `every`؛ O(a×s) | Set با زمان O(a+s)؛ حافظه اضافه O(s) |
| selector صفحه اعلان‌ها | بازسازی Map و آرایه در هر فراخوانی | محاسبه فقط هنگام تغییر ورودی‌ها؛ نتیجه با هویت پایدار |
| فهرست پروژه‌ها و باگ‌ها | آرایه‌های تازه حتی با داده یکسان | memoization و حذف تعدادی آرایه میانی |
| `/auth/me` | دریافت دوباره کاربر، مجوزها و گاهی تخصیص‌ها بعد از middleware | استفاده از context تازه بررسی‌شده همان درخواست |
| آپلود POC | عملیات همگام filesystem و خواندن فایل headers پیش از رد اندازه غیرمجاز | عملیات async و رد اندازه نامعتبر پیش از خواندن محتوا |
| وضعیت رابط | تعدادی Effect با setState و commit اضافه | همگام‌سازی شرطی state پیش از commit و ثابت‌کردن ورودی‌های memo |
| ساعت deadline | محاسبه وابسته به رندر اتفاقی | ساعت مشترک دقیقه‌ای با یک timer برای badgeهای نصب‌شده و پاک‌سازی پس از unmount |

برای الگوریتم گروه‌بندی، خروجی نسخه قبلی و جدید با `deepEqual` مقایسه شد. روی این دستگاه، میانه ۵ اجرا برای ۱۰٬۰۰۰ اعلان متعلق به یک کاربر از **۴۳٫۸۰ میلی‌ثانیه** به **۰٫۱۱۶ میلی‌ثانیه** رسید. این microbenchmark شامل دیتابیس، شبکه و رندر نیست و درصد بهبود کل برنامه از آن قابل استنتاج نیست. استفاده از Map/Set در بعضی بخش‌ها زمان را با مصرف حافظه کمکی بیشتر معاوضه می‌کند؛ ادعای کاهش هم‌زمان حافظه همه بخش‌ها مطرح نیست.

### اندازه خروجی فرانت‌اند

شرط تشخیص بسته React در Vite قبلاً بسته‌هایی مانند `react-router` و `recharts` را نیز با پیشوند مشترک وارد همان گروه می‌کرد. همچنین تمام بسته‌های متفرقه در یک vendor مشترک قرار می‌گرفتند. تشخیص بسته‌ها دقیق شد و تقسیم وابستگی‌های مسیرهای lazy به bundler سپرده شد.

مقایسه با سورس و dependency یکسان و فقط پیکربندی chunk متفاوت:

| مجموع فایل‌های JS ارجاع‌داده‌شده در HTML خروجی | پیکربندی قبلی | پیکربندی جدید |
| --- | ---: | ---: |
| حجم خام | 1,442,917 بایت | 996,074 بایت |
| مجموع gzip محلی | 409,095 بایت | 285,368 بایت |

کاهش حجم gzip این مجموعه حدود **۳۰٫۲٪** است. این اندازه‌گیری artifact است؛ اندازه‌گیری زمان بارگذاری واقعی مرورگر یا شبکه نیست. هشدار chunk بالاتر از ۵۰۰ کیلوبایت در build نهایی نیز برطرف شد.

## حفظ رفتار و سازگاری

- ثبت‌نام معمولی با آواتار، نقش پیش‌فرض، مجوزهای سمت سرور و فرمت پاسخ‌های API حفظ شده‌اند. عملیات غیرمجاز امنیتی عمداً محدود شده‌اند.
- مدل‌های legacy، نام collectionها، قراردادهای مشترک و سازگاری فیلدهای قدیمی حذف نشده‌اند.
- چهار تست اولیه جدول پروژه با registry فعلی ناسازگار بودند: ستون اجباری گزارش، action تخصیص اعضا و نمایش ستون باگ در pentest. انتظار تست‌ها با قرارداد موجود تطبیق داده شد؛ منطق تجاری برای عبور این تست‌ها تغییر نکرد.
- تنظیم ESLint برای TypeScript به بررسی شناسه‌های خود TypeScript تکیه می‌کند؛ فایل‌های vendor از lint کد اختصاصی کنار گذاشته شده‌اند. خطاهای واقعی کد اختصاصی، کلیدهای React و مشکلات state/effect اصلاح شده‌اند.
- تست HTTP از سرور loopback و پوشه موقت استفاده می‌کند و مدل‌های دیتابیس را mock می‌کند. این تست اتصال واقعی MongoDB را اثبات نمی‌کند.

## مواردی که هنوز در محیط واقعی باید بررسی شوند

1. مرورگر متصل در این محیط موجود نبود؛ تست بصری و گردش کامل کاربر با نقش‌های واقعی اجرا نشد. قبولی تست‌ها تضمین مطلق عدم regression نیست.
2. اتصال به دیتابیس production، آزمون بار با داده واقعی، `explain` کوئری‌ها، و اجرای `nginx -t` روی سرور مقصد انجام نشده است. ایندکس‌های افزایشی شواهد در اولین راه‌اندازی بعدی ساخته می‌شوند و روی دیتابیس بزرگ زمان و فضای دیسک می‌خواهند.
3. مسیرهای تست‌کیس QA، تیکت و فهرست/ایجاد deployment در نسخه موجود عمدتاً placeholder هستند: آرایه خالی یا echo بدنه درخواست برمی‌گردانند. تبدیل آن‌ها به قابلیت پایدار نیازمند تعریف رفتار و ذخیره‌سازی است و در این اصلاح امنیتی، رفتار جدید برایشان اختراع نشده است.
4. بعضی فهرست‌های قدیمی، از جمله فهرست کاربران و وظایف، صفحه‌بندی اجباری ندارند. افزودن اجباری pagination بدون تغییر هماهنگ قرارداد و رابط می‌تواند داده‌ها را از دید کاربران پنهان کند؛ benchmark دیتابیس و طراحی سازگار آن هنوز لازم است.
5. حساب‌هایی که قبلاً با رمز ثابت seed ساخته شده‌اند خودکار تغییر رمز نداده‌اند. در محیط مربوطه باید رمز قوی انتخاب و بازنشانی کنترل‌شده انجام شود. فایل‌های مشکوک قدیمی نیز در این بررسی حذف نشده‌اند.
6. اعتبارسنجی امضای فایل، آنتی‌ویروس یا بازرمزگذاری کامل تصویر نیست. آپلود ناشناس موردنیاز ثبت‌نام با محدودیت نوع، اندازه، تعداد و نرخ حفظ شده است؛ سیاست نگهداری فایل‌های بدون استفاده نیازمند تصمیم عملیاتی است.
7. هماهنگی بین تب‌ها به پشتیبانی Web Locks در مرورگر وابسته است؛ هماهنگی درخواست‌های هم‌زمان در یک تب مستقل از آن انجام می‌شود.

## اجرای مجدد بررسی‌ها و اعمال در استقرار

در ریشه مخزن، با Node سازگار با پروژه:

```bash
npm test
npm run typecheck
npm run lint
npm run build
npm run index:project:check
npm audit
```

تست API به اجازه ساخت سرور loopback و فایل موقت نیاز دارد. اسکریپت‌های `test:api` و `test:web` نیز جداگانه قابل اجرا هستند.

برای ایجاد ادمین اولیه، `SEED_ADMIN_PASSWORD` را از طریق محیط امن فرایند مقداردهی کرده و `npm run seed:api` را اجرا کنید. برای تغییر عمدی رمز ادمین موجود، علاوه بر رمز جدید، `SEED_ADMIN_RESET_PASSWORD=true` لازم است. seed روی دیتابیس واقعی در این بررسی اجرا نشده است.

تغییرات Nginx و dependencyها هنوز deploy نشده‌اند. استقرار باید lockfile جدید را نصب کند، build جدید را اجرا کند و پیکربندی Nginx را پس از بررسی روی همان سرور reload کند. حذف یا مهاجرت اسناد دیتابیس بخشی از این تغییر نیست.
